# User-Capability-Aware Execution — 详细模式

本文档是 `SKILL.md` 中"User-Capability-Aware Execution（2026-06-01 用户信号）"段的**实操展开**。

## 用户原话（2026-06-01）

> "我其实没法 review，我也看不太懂，我也只能看实际效果。必须全量安装 skill-creator（已发 skills-main.zip）"

这句话的**三层意思**：
1. **没有 review 能力**——不想被问"这一步要 X 还是 Y"
2. **看不太懂**——技术细节（diff stat、commit hash、branch 关系）对他没意义
3. **只看效果**——最终能跑、装好、命令返回预期结果 = 成功

## 核心判断规则

| 类别 | 例子 | 处理 |
|------|------|------|
| **方向选择**（影响最终结果）| 选 A / 选 B / 命名 / 仓库结构 | ✅ **问**（用户能答）|
| **过程细节**（不影响最终结果）| 拆几个 commit、commit message 措辞、commit 顺序 | ❌ **不问**（自动决定）|
| **执行模式**（superpowers 流程内部）| Subagent-driven vs Manual | ❌ **不问**（默认直接干）|
| **验收形式**（怎么让用户验证）| 给命令 + 预期输出 | ❌ **不问**（给清单）|

**关键判断**：「用户能拍板 = 问；过程性细节 = 自动化」。

## ⭐ 进度汇报铁律（2026-08-03 用户强烈反馈）

**用户原话**：「你又不向我确认，又不向我汇报，又不显示进度」「我都会把你卸载掉了」

**根因**：本文件下方「完成一个 task 后**不要立刻向用户报告**——先**自验**」被误读为「执行全程不汇报」。实际含义是「自验后再报，不是不报」。

**铁律**：
1. **"不打断"≠"不汇报"**——不打断指不问过程性 X/Y 选择；每步完成必须汇报结果（1-2 句话）
2. **长耗时操作必须主动报进度**——镜像拉取、构建、大文件下载等 >2 分钟的操作，每隔几分钟主动查进度并汇报，不等用户问
3. **阻塞/超时立即报**——子 agent 超时、网络断连、重试失败，第一时间告诉用户，不自己跳过或换方案
4. **plan 变更先确认**——审查未过、方案偏离，必须回来找用户确认新方向，不自行继续

**反模式**（本机 2026-08-03 实战）：
- 镜像拉取 20+ 分钟，期间用户多次问「进度如何」，agent 没有主动汇报
- 对抗审查子 agent 超时，agent 自己跳过审查继续执行，没告诉用户
- docker compose 后台跑了 30 分钟，用户完全不知道在干什么

**汇报模板**（≤3 行）：
```
做了什么：<1 句>
当前状态：<数字/百分比/具体结果>
下一步：<1 句，如果是等待就说"完成会自动通知">
```

## 每个 task 完成后的自我验证清单

完成一个 task 后**不要立刻向用户报告**——先**自验**。但**自验通过后必须报结果**（见上方「进度汇报铁律」）。检查项：

### 1. 文件存在性
- 这个 task 承诺创建的文件确实创建了
- 大小 > 0
- 路径正确

### 2. frontmatter 完整性
- name / description 字段都在
- description 字符数 ≤ 1024（超过会被截断）
- metadata.hermes 块（如果用了）完整
- YAML 语法解析无错

### 3. git 状态
- `git status` 干净（无未提交）
- commit 在正确的分支上
- diff stat 范围符合预期（**这次踩坑**：reset + restore 后 diff 从 +7 行变成 +184 行——必须看 stat 才看出问题）

### 4. 跨文件引用一致
- SKILL.md 引用的 references/*.md 实际存在
- 引用的 skill name 在 skills_list() 里能找到
- 链接的 GitHub URL 跟 `git remote -v` 一致（见 references/skill-bundling-patterns.md）

### 5. 用户能看到效果
- 给他能跑的命令（不是描述）
- 命令的预期输出（不是"应该会成功"）

**自验失败 = 不报完成 = 回去修**。**自验通过 = 报完成 + 给用户验收清单**。

## 给用户的验收清单模板

不是写"已完成 X"，而是写**用户能跑的具体命令**：

```bash
# 1. 目录存在
ls /path/to/expected/dir
# 预期: 看到 file1 file2 file3

# 2. frontmatter 有效
head -20 /path/to/SKILL.md
# 预期: 看到 --- 块和 name/description

# 3. 状态干净
cd /path/to/repo && git status
# 预期: nothing to commit, working tree clean

# 4. 引用的文件都在
test -f references/foo.md && echo "✓ foo.md exists"
```

**为什么用 `ls / head / test -f`**：用户不需要懂 git 也不需要懂 YAML——`ls` 出文件就行。

## 何时**必须**打断用户

虽然说"不问过程细节"，但以下情况**必须**打断：

1. **发现多个合理方案**——影响结果的方向选择
2. **网络/认证问题**——超出本机能解决的范围
3. **关键决策**——比如删文件、改 remote、删 fork 仓库
4. **用户说"停"**——任何时候

**反例（不打断）**：
- commit 拆几个 = 过程细节
- 命名 = 拍板
- 文件位置 = 拍板
- commit message 措辞 = 过程细节
- 多个 stash / branch 怎么管 = 过程细节

## 错误处理：发现自己的改动超出范围时

**本次踩坑（2026-06-01）**：
- 我以为只改了 darwin-skill 的 frontmatter 7 行
- 实际 diff stat 显示 +184 行
- 根因：reset 之后 SKILL.md 跟 origin/dev 不一致，restore 用了错的"原始备份"
- **用户看不到 diff stat**——只能看到"commit 完成"消息

**修复**：
- **每个 commit 前** `git diff --cached --stat` 检查范围
- 数字异常 = 立刻 `git diff` 看具体内容
- 范围超预期 = 不 commit，先 reset + 重做

## superpowers 阶段对应表

| 阶段 | 用户能 review 时 | 用户不能 review 时 |
|------|------------------|-------------------|
| **Phase 1 Brainstorm** | 一次一问，给选项 | 一次一问，给选项（**这部分不变**——用户能答方向） |
| **Phase 2 Plan** | 给完整 plan，问 OK 吗 | 给完整 plan + 写完即开干（不问"subagent vs manual"） |
| **Phase 3 每个 task** | 等用户报 commit 再下一个 | **自动 commit** + 自验清单（不打断） |
| **Phase 3 中间决策** | 问"X 还是 Y" | 查 superpowers 原则**自动选**（不打断） |
| **Phase 5 Finish** | 给 4 options 选 | **默认 Subagent-Driven + push 后让用户验** |
| **最后** | 报"完成" | 给**用户验收清单**（具体命令 + 预期输出） |

## 怎么识别"用户能不能 review"

不必问用户"你能不能 review"——**观察对话模式**：
- 用户**常用短句**直接确认/纠正 → 高 review 能力 → 默认模式
- 用户**少用技术词**、常说"不太懂"、"看效果" → 低 review 能力 → 本模式
- 用户**有耐心**等长回复 → 高 review 能力
- 用户**嫌长**、要求"直接干" → 低 review 能力

**判断保守**：宁可假设用户 review 能力低，多给命令少给描述。
